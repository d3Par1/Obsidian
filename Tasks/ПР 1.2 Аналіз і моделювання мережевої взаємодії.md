### 1. Учасники взаємодії
- [ ] Визначити учасників: **клієнти, сервери, проміжні вузли** (брокер, балансувальник, реле тощо)

### 2. Діаграма послідовності (UML Sequence Diagram)
- [ ] Лінії життя для всіх учасників
- [ ] Порядок повідомлень **у часі**: запит → обробка → відповідь → підтвердження отримання
- [ ] Показати очікувані відповіді (синхронні / асинхронні повідомлення, return-стрілки)
- [ ] Бажано: альтернативні фрагменти `alt` / `opt` / `loop` для помилок, тайм-аутів, повторів

### 3. Діаграма взаємодії (UML Communication Diagram)
- [ ] Ті самі об'єкти, розташовані **у просторі** (зв'язки між об'єктами)
- [ ] Пронумеровані повідомлення вздовж зв'язків (1, 1.1, 2 …)
- [ ] Має бути семантично еквівалентна діаграмі послідовності (див. рис. 4 методички — перетворення однієї в іншу)

### 4. Схема алгоритму (системи або окремої функції)
- [ ] Блок-схема за ГОСТ / ДСТУ (як рис. 5–6 методички)
- [ ] Відобразити не лише внутрішню логіку, а й **послідовність мережевої взаємодії**:
  - [ ] створення та налаштування сокета
  - [ ] формування повідомлення
  - [ ] передавання
  - [ ] очікування та отримання відповіді
  - [ ] перевірка отриманих даних
  - [ ] оброблення помилок
  - [ ] завершення або повторення операції

### 5. Формат повідомлення (мінімум одного типового)
- [ ] **Заголовки**
- [ ] **Службові поля** (тип, id / послідовний номер, довжина, timestamp, версія, контрольна сума тощо)
- [ ] **Дані** (payload)
- [ ] Таблиця «поле — тип — розмір — призначення» + приклад повідомлення (JSON / бінарний)

### 6. Особливості TCP та UDP як транспортного рівня
- [ ] Що змінюється в протоколі взаємодії при роботі поверх **TCP**: з'єднання, потік байтів → потрібне **кадрування** повідомлень (довжина / роздільник), порядок і доставка гарантовані, keep-alive, обслуговування кількох клієнтів
- [ ] Поверх **UDP**: дейтаграми, можлива втрата / дублювання / зміна порядку → потрібні **seq-номери, ACK, тайм-аути, повтори**, обмеження розміру дейтаграми
- [ ] Які функції системи краще робити на TCP, а які на UDP, і чому
- [ ] (з ПР 1.1) як це співвідноситься з WebSocket

## Теорія для звіту (коротко)

- **Діаграма послідовності** показує порядок обміну повідомленнями **у часі**: які повідомлення, в якому порядку, які відповіді очікуються.
- **Діаграма взаємодії** — розширення діаграми об'єктів: об'єкти + повідомлення між ними, розташовані **у просторі**.
- Обидві семантично еквівалентні й взаємно перетворювані. Послідовності вживають частіше; взаємодії краще показують зв'язки між об'єктами й допомагають перевірити діаграму класів.
