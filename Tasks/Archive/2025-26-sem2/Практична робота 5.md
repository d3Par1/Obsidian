1. Теорія 


1.1.  Типові проблеми, які виникають при роботі з пам’яттю в Linux
Ці проблеми є частими причинами багів у продакшн-програмах, особливо в C/C++, де керування пам’яттю виконується вручну. Навіть такі незначні помилки, як a[3] замість a[2], можуть:
* руйнувати структури даних
* викликати аварійне завершення (segfault)
* спричинити витоки та повільне падіння продуктивності.

1.2.  Приклади з ASCII-візуалізаціями
1. Неініціалізовані змінні
int main() {
    int x;
    printf("x = %d\n", x); // Значення x не визначене
    return 0;
}
//Це не UB, але може виводити випадкові значення, оскільки стек містить "сміття".


2.  Вихід за межі масиву (Out-of-bounds)
int a[3] = {1, 2, 3};
a[5] = 42; // Доступ за межами масиву
Схематичне поясненн коду
a[0] a[1] a[2] ??  ??  a[5]
  1    2    3   ?   ?   ← 42 тут — заборонений доступ
3. Витік пам’яті (Memory Leak)
void leak() {
    int *p = malloc(100 * sizeof(int));
    // жодного free() → витік
}
//Після завершення функції вказівник зникає, а виділена пам’ять – залишається зайнятою.
4. Невизначена поведінка (Undefined Behavior)
int a = 10;
int b = a++ + ++a; // UB: порядок виконання не визначено
Вираз a++ + ++a може дати різний результат на різних компіляторах.
5. Фрагментація пам’яті (Fragmentation)
char *a = malloc(8);
char *b = malloc(128);
char *c = malloc(8);
free(b); // Звільняємо великий блок між двома маленькими




[ a:8B ][ b:128B ][ c:8B ]
     ↓ free()
[ a:8B ][  F R E E ][ c:8B ]


// Після цього виділити великий блок НЕМОЖЛИВО → фрагментація
6. "Завислий" покажчик (Dangling pointer)
int *p = malloc(sizeof(int));
*p = 42;
free(p);
printf("%d", *p); // доступ до вже звільненої пам’яті
//Може випадково вивести правильне значення, але це undefined behavior.


7.  Подвійне звільнення (Double Free)
int *p = malloc(sizeof(int));
free(p);
free(p); // Помилка: подвійне звільнення
 :
//Може призвести до краху або компрометації безпеки (heap poisoning).
8.  Переповнення буфера (Buffer Overflow)
char *p = malloc(10);
free(p);
p[0] = 'A'; // використання звільненої пам’яті
        Перезапис пам’яті, що може змінити змінні або return-адресу в стеку.
9.  Use-after-free
char *p = malloc(10);
free(p);
p[0] = 'A'; // використання звільненої пам’яті
10. Пошкодження пам’яті (Memory Corruption)
int a[3] = {1, 2, 3};
int b = 5;
a[5] = 99; // змінює пам’ять змінної b або інші структури
//Може потайки зіпсувати дані в іншій частині програми.

С
// leak.c
#include &lt;stdlib.h>


int main() {
    int *ptr = malloc(100 * sizeof(int)); // виділення пам'яті

Додаткові параметри Valgrind:
Параметр
	Опис

	Повний звіт про витоки пам’яті
	--show-leak-kinds=all
	Показати всі типи витоків (definitely, indirectly, etc.)

	Показує, звідки взялася "сміттєва" пам’ять (use of uninitialized mem)
	--log-file=valgrind.log
	Зберегти результат у файл
	



   2. Практика
2.1.  Варіанти завдань
   1. Змоделювати читання за межами масиву, яке не викликає segfault, але змінює логіку обчислень через “витік” сусідньої змінної зі стеку.
   2. Створити приклад, де переповнення цілочисельного розміру призводить до виділення занадто малого блоку і подальшого тихого пошкодження heap-метаданих.
   3. Реалізувати сценарій use-after-free, який проявляється лише після кількох успішних повторних алокацій того ж розміру.
   4. Зробити подвійне звільнення, яке інколи не падає через кешування малих блоків (tcache), але руйнує внутрішній стан allocator.
   5. Створити витік пам’яті, який виникає тільки при помилці системного виклику і не проявляється у “успішному” сценарії.
   6. Побудувати приклад фрагментації, де велика алокація неуспішна, хоча сумарно вільної пам’яті достатньо.
   7. Зробити запис за межі локального масиву так, щоб перезаписати іншу локальну змінну без краху.
   8. Реалізувати некоректний виклик realloc, що втрачає дані при невдалому розширенні буфера.
   9. Змоделювати помилку, коли free() викликається у двох різних гілках логіки, але лише при певній послідовності викликів.
   10. Побудувати випадок, де збережений вказівник “всередину” блоку призводить до неможливості коректного звільнення базової адреси.
   11. Реалізувати помилку через неправильний sizeof (використання sizeof(ptr) замість sizeof(*ptr)), яка проявляється лише при зміні архітектури.
   12. Створити приклад, де memcpy перезаписує padding у структурі, що призводить до некоректної поведінки при іншому вирівнюванні.
   13. Змоделювати COW-поведінку після fork(), де зміна одного байта призводить до різкого зростання RSS.
   14. Побудувати сценарій, у якому malloc повертає успіх для великого розміру, але процес завершується пізніше через OOM при записі в сторінки.
   15. Реалізувати циклічну структуру даних, де звільнення одного вузла робить інші недосяжними для cleanup.
   16. Створити приклад, де невірне приведення типів призводить до втрати старших бітів адреси на 64-бітній системі.
   17. Побудувати багатопоточний сценарій, де один потік звільняє пам’ять, яка ще використовується іншим.
   18. Реалізувати сценарій, де mmap-виділення не звільняється при помилковому шляху завершення, але не детектується стандартним аналізом витоків.
